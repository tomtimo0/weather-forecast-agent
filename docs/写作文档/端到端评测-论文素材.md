## 一、实验设计

### 1.1 对照设计：full vs ablated（保留输入侧公平）

两档共享：
- **同一个 LLM**（GLM-5.1，温度 0）
- **同一份意图识别 + 参数补全前置**（保证输入解析完全一致）
- **同一份 9 个气象 API 工具**（保证数据获取能力一致）

**关键差异**只在「拿到 API 数据后如何解读」：

| 档位 | 工具集 | System Prompt 段 |
|---|---|---|
| `full` | 9 API + ``search_knowledge`` + ``bridge_weather_data`` | 完整，含「RAG 知识检索规则」+「语义桥接调用约束」 |
| `ablated` | 仅 9 API | 删除上述两段，模拟"不做双通路 RAG 的常规工程做法" |

这是干净的"通路 B / 通路 A 双通路 RAG 的端到端价值"测试——不掺杂工具调用
能力差异、不掺杂上下文理解差异。

### 1.2 评测集：30 条用例 / 6 类真实场景

| 场景类别 | 用例数 | 设计要点 |
|---|---:|---|
| `simple_query` | 5 | 单城市单要素的实时/明天天气 |
| `multi_compare` | 5 | 多城市对比（≥2 个城市） |
| `trend_analysis` | 5 | 一周温度/降水趋势 |
| `extreme_search` | 5 | 找最热/最冷/最大降水的具体哪一天 |
| `decision_support` | 6 | 户外/洗车/带伞/跑步/防晒/驾驶决策 |
| `warning_extreme` | 4 | 暴雨/强对流/严寒/台风预警 |

**关键设计**：评测集**完全基于真实和风天气 API + Open-Meteo API 跑实时数据**，
而非构造假数据；评测断言全部用「**结构性证据**」（如"必须含温度数值"、
"必须给具体日期"），不依赖具体数值，保证可重复性。

### 1.3 5 类断言指标

```
对每条用例的 agent 回答，断言：

1. key_facts        从用例自带词表/正则中匹配 → recall
2. citation         是否含 GB/T xxx-yyyy 等标准号
3. grading          是否使用规范气象分级词（小雨/暴雨/3级风/严寒/雾 等）
4. advice           是否给出明确决策建议
5. judge_score      LLM-as-judge 4 维度（事实/完整/专业/流畅）打分

case_pass = key_fact_recall ≥ 0.8
            AND（按用例条件断言 citation/grading/advice）
            AND judge_overall ≥ 3.0
```

## 二、核心结果

### 2.1 双档总表（30 用例）

| 指标 | ablated | full | 差距 |
|---|:---:|:---:|:---:|
| **端到端通过率（核心）** | 73.3% | **86.7%** | **+13.4 pp** |
| 关键事实点 recall | 99.2% | 99.2% | 持平 |
| **权威标准引用率** | **0.0%** | **26.7%** | **+26.7 pp** |
| 规范分级出现率 | 100.0% | 96.7% | -3.3 pp |
| 决策建议出现率 | 90.0% | 83.3% | -6.7 pp |
| Judge 事实性（0-5） | 4.07 | 3.90 | -0.17 |
| Judge 完整性（0-5） | 4.93 | 4.87 | -0.06 |
| **Judge 专业性（0-5）** | 3.10 | **3.47** | **+0.37** |
| Judge 流畅性（0-5） | 4.97 | 5.00 | +0.03 |
| Judge 综合（0-5） | 4.27 | 4.31 | +0.04 |
| 平均工具调用次数 | 3.67 | 4.57 | +0.90 |

### 2.2 按场景类别拆分（端到端通过率）

| 类别 | 用例数 | ablated | full | 差距 |
|---|---:|:---:|:---:|:---:|
| **decision_support** | 6 | **50.0%** | **100.0%** | **+50.0 pp** |
| `warning_extreme` | 4 | 50.0% | 75.0% | +25.0 pp |
| `simple_query` | 5 | 80.0% | 80.0% | 0 |
| `extreme_search` | 5 | 80.0% | 80.0% | 0 |
| `trend_analysis` | 5 | 80.0% | 80.0% | 0 |
| `multi_compare` | 5 | 100.0% | 100.0% | 0 |

**关键观察**：

1. **决策类场景全部通过**（full 6/6 vs ablated 3/6）—— 双通路 RAG 在决策场景下
   价值最高，正是"是否适合 X" 这类问题最依赖权威标准引用支撑。
2. **预警类场景显著提升**（full 75% vs ablated 50%，+25 pp）—— 暴雨/严寒等
   阈值判断需要 GB/T 标准支撑。
3. **简单查询/对比/趋势/极值场景持平** —— 这类场景下信息检索本身已足够，
   RAG 不会带来端到端通过率的差异（虽然引用率仍有差距）。

### 2.3 按场景类别拆分（权威标准引用率）

| 类别 | ablated | full | 差距 |
|---|:---:|:---:|:---:|
| **decision_support** | 0% | **50%** | +50 pp |
| `simple_query` | 0% | 40% | +40 pp |
| `warning_extreme` | 0% | 25% | +25 pp |
| `trend_analysis` | 0% | 20% | +20 pp |
| `extreme_search` | 0% | 20% | +20 pp |
| `multi_compare` | 0% | 0% | 0 |

**关键观察**：ablated 档**所有 30 条回答全部 0% 引用** —— 即使它"知道"某个
阈值（如"暴雨为 24h ≥ 50mm"），也不会主动告诉用户出处来源。这是 LLM 的
经典行为：**事实性 OK，可溯源性 0**。

## 三、典型对照案例（论文卖点）

### 3.1 案例 A：暴雨判定（warning_001_rainstorm）

**用户查询**："未来三天上海会有暴雨吗？"

**ablated 回答（节选）**：

> 5月7日虽然有小雨，但降雨量很小，远未达到暴雨级别（**暴雨标准为24小时
> 降水量 ≥ 50mm**）。

→ 数值正确，但**纯粹"信我"的 LLM 表述**，用户无法验证"50mm"出处。

**full 回答（节选）**：

> ### 📋 暴雨判定依据
> 依据 **中国气象局·降水量等级（GB/T 28592-2012）§4.1**：
> - **24 小时降水量 50.0~99.9mm** 为暴雨
> - **12 小时降水量 30.0~69.9mm** 为暴雨

→ 直接引用 GB/T 标准号 + 具体条款 + 双时段双区间，这是 ablated 完全做不到的。

### 3.2 案例 B：洗车决策（decision_002_carwash）

**用户查询**："今天北京适合洗车吗？"

**ablated 回答**：直接给"洗车指数 1 级（适宜）"，建议"今天可以放心洗车"。
但**完全没说"1 级（适宜）"的来源依据**。

**full 回答（结尾）**：

> 📌 洗车指数依据：**中国气象局天气生活指数分级标准**，1 级为最适宜等级。

→ full 还诚实承认了 RAG fallback：开头一句"知识库中没有直接关于洗车指数的
分级标准"——这是 RAG 系统在缺乏对应条款时的可控降级，比 ablated 的"装作
什么都知道"更负责任。

### 3.3 失败案例（4 条 full 也未通过）

`simple_005_today_wind` / `trend_002_high_temp` / `extreme_004_max_wind`
/ `warning_003_severe_cold` —— 这 4 条 full 档失败的共同原因都是**缺权威
引用**，但仔细看 judge comment 会发现：full 档其实**已经引用了"≥35°C 高温
标准"、"严寒/寒冷分级"等具体阈值**，只是 LLM 没主动写出 GB/T 编号。

这反映了 full 档的改进空间：**RAG 检索到的知识被 LLM 用了，但出处编号在
最终报告生成时被 LLM 省略**。这一现象即是 7.13 节"LLM 即使在 RAG 兜底
下，也会有 25.4% 的引用幻觉/遗漏率"的端到端体现，与通路 B 的 LLM 引用
缺失率（~75%）相比已大幅改善（**26.7% > 0%**），但仍未达到 100%。

## 四、Judge 专业性差距与"看似平局"的解读

### 4.1 综合分接近的成因

注意一个看似反常的数据：

```
ablated  Judge 综合 = 4.27
full     Judge 综合 = 4.31    ← 仅 +0.04
```

但拆分到 4 个维度：

| 维度 | ablated | full | 差距 |
|---|:---:|:---:|:---:|
| 事实性 | 4.07 | 3.90 | -0.17 |
| 完整性 | 4.93 | 4.87 | -0.06 |
| **专业性** | 3.10 | **3.47** | **+0.37** |
| 流畅性 | 4.97 | 5.00 | +0.03 |

差距集中在**专业性（+0.37）**。事实性 / 完整性 / 流畅性接近持平甚至 ablated
略胜——这与直觉相反，但其实是 LLM-as-judge 的特性：

- **ablated 的回答看起来很完整、很流畅**（毕竟它是 LLM 的拿手好戏——"装作什么
  都知道"）
- 但只要看「**专业性**」这一专门关注"分级 + 引用 + 阈值依据"的维度，full
  优势立显（+0.37）

### 4.2 端到端通过率给出更严格的真相

Judge 综合分（4 维度等权平均）会"稀释"专业性的劣势，但论文核心指标
"**端到端通过率**" 把"该引用时必须引用"作为硬条件——

```
ablated 端到端通过率 = 73.3%
full    端到端通过率 = 86.7%
差距 = 13.4 pp
```

这才是真实的、面向用户决策可用性的差距——**ablated 看起来好，但 26.7% 的
情况下其回答不能拿来做权威决策**。

## 五、端到端评测对论文 Q1+Q2+Q3 的总实证价值

### 5.1 与此前 4 个单模块评测的关系

到目前为止，论文已积累 5 组实证：

| 实证 | 评测对象 | 关键数据 | 视角 |
|---|---|---|---|
| 数据真实性 | KB 12 项标准人工核对 | 修正 7 处错误 | 数据层 |
| 通路 A 检索 | RAG 60 条 | top-1 85% / Recall@5 97.7% | 单模块 |
| 通路 B 桥接 | 71 条 / 9 类要素 | grade_id 100% / citation 100% | 单模块 |
| 意图理解 | 35 条 / 10 类 | E2E 91.4% / 角色 100% | 单模块 |
| 代码执行 | 18 条 / 6 类 | +22.2 pp 数值准确率 | 单模块 |
| **端到端**（本节） | **30 条 / 6 类** | **+13.4 pp 任务完成率** | **整体系统** |

前 5 组都是「中间产物」视角，本节首次以**用户最终体验**视角验证整套系统的
端到端价值。**单模块成绩好不一定端到端就好**——例如通路 B 单测 citation
真实性 100%，但端到端只有 26.7%（因为 LLM 在最终报告生成时仍可能省略出处），
这是单模块评测无法捕捉的「集成衰减效应」，端到端评测专门补足了这块空白。

### 5.2 与开题报告承诺的对应

开题报告 §3.4 明确承诺**五个评测指标**：

| 开题承诺 | 完成状态 | 评测出口 |

| 报告生成质量（BLEU/ROUGE/judge） | ✅ | **本节 LLM-as-judge 4 维度打分** |

**开题报告承诺的 5 项指标至此全部完成**——论文 5.2 节"典型气象任务场景下的
技术验证"具备完整的实证支撑。

## 六、运行可重现性

```bash
# 完整 30 用例 × 2 档评测（首次约 60-90 分钟，缓存后约 5 秒）
python -m experiments.eval.run_e2e_eval

# Smoke test：仅前 N 条 + 仅一档（调试用）
python -m experiments.eval.run_e2e_eval --limit 3 --only-mode ablated

# 强制重跑（清空三层缓存）
python -m experiments.eval.run_e2e_eval --force-llm
```

输出：

- `experiments/results/e2e_eval_<timestamp>.{json,md}`
- `e2e_eval_latest.md` 自动镜像最新版
- `e2e_intent_cache.json`：意图识别 + 补全前置缓存
- `e2e_agent_cache.json`：(query, mode) → agent 完整输出（含工具调用 trace）
- `e2e_judge_cache.json`：(query, answer) → 4 维度 judge 打分

修改 prompt / 评测断言会通过版本号让缓存自动失效。

### 6.1 已知工程要点

1. **max_iters 默认 30**：full 档因为双通路 RAG 需要 8-12 次 stream chunk，
   不能设得太紧（最初 12 导致 4 条空回答，已修复）
2. **意图前置缓存**：两档共享同一份意图识别结果（同 query 在 ablated/full
   下解析结果相同），节省一半 LLM 调用
3. **真实 API 数据**：评测调用真实和风天气 + Open-Meteo API（不 mock），数据
   每次不同——评测断言聚焦「结构性证据」保证可重复性
4. **稳定性加固**：所有 LLM 调用带 `timeout=60-90s` + `max_retries=2`，主循环
   `try/finally` + 每条用例增量落盘三层缓存，可在任意时刻 KeyboardInterrupt
   并断点续跑
