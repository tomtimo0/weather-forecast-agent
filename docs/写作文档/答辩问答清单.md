# 本科毕业论文答辩｜可能问题清单与参考答案

> 本文档按"基础概念 → 设计选择 → 核心创新细节 → 评测真实性 → 学术诚信 → 价值与未来"6 个维度组织 60+ 道高频问题，每题给出可直接背诵的简短答案与可拓展的延伸要点。
>
> **答辩临场策略**：① 不知道就直接说"这个问题我考虑还不够深入，会后向老师请教"，比硬答错好；② 凡涉及具体数字必须用论文里的同一组数（91.4 / 85.0 / 100 / 88.9 / 86.7 / 74.6 pp / 22.2 pp / 26.7 pp / 13.4 pp）；③ 凡被追问"你确定吗"，先复述对方关键词再答，给自己半秒思考时间。

## 一、基础概念盲点（评审随机抓问）

### Q1. 什么是 ReAct 范式？为什么选它？
ReAct 是 Yao et al. 2023 年提出的 Reasoning + Acting 交替范式，让大语言模型在每一步既输出思考链 (Thought) 又输出工具调用 (Action)，再根据返回 (Observation) 进入下一轮，就是所谓的实践，认识再实践。直到产出最终答案。它相对纯 Chain-of-Thought 的优势是能借助外部工具消除幻觉，相对纯 Function Calling 的优势是显式保留推理痕迹便于调试。本文选 ReAct 是因为气象任务需要多步检索与计算，且强调可解释性。

### Q2. 什么是 RAG？和直接微调有什么区别？
RAG 是 Retrieval-Augmented Generation 的缩写，由 Lewis et al. 2020 年提出，做法是先用检索器把外部知识取出来注入 prompt，再让大模型基于这段证据生成答案。相对微调，RAG 不修改模型权重，知识更新只需要增删向量库，部署成本低、可追溯性强；但代价是每次推理都要付出检索延迟。本文气象国标条款经常更新，且要求引用真实，因此 RAG 比微调更合适。

### Q3. 什么是 Agent？和普通 Chatbot 的区别？
Agent 是能感知环境、自主规划、调用工具并迭代修正的智能实体。相对普通 Chatbot 只做一问一答的文本生成，Agent 多了三件事：① 显式工具调用能力（Function Calling 或类似机制）；② 多步规划与状态保持；③ 失败重试与异常处理。本文实现的就是一个对外暴露 11 个工具单元、支持多轮对话状态保持的单 Agent。

### Q4. 什么是 Function Calling？
Function Calling 是 OpenAI 在 2023 年推广的能力，让大模型按照 JSON Schema 输出结构化的函数名 + 参数，由外部框架真正执行后再把结果回填给模型。它把"模型生成自由文本，再用正则解析参数"的脆弱方案，升级为模型直接受 Schema 约束输出，参数解析准确率大幅提升。本文 11 个工具单元的 Schema 都遵循这一规范。

### Q5. 什么是 BM25？为什么和向量检索一起用？
BM25 是经典的词法检索算法，基于词频与逆文档频率，对关键词精确匹配能力强，但对同义词、改写敏感。向量检索（这里用 BAAI/bge-m3 1024 维嵌入）擅长语义相似但词面不一致的场景，可对低频术语召回不稳定。两者权重融合就是经典的 hybrid search 方案，能同时覆盖关键词命中与语义相似两类查询，在本文 60 条检索评测上 Top-1 命中率 85.0%。

### Q6. 什么是 Top-K 命中率、MRR、Recall？
- **Top-K 命中率**：正确答案是否出现在前 K 条返回中，命中算 1 不命中算 0，按 K 取均值。
- **MRR (Mean Reciprocal Rank)**：取正确答案在返回列表中的倒数排名再求均值，0~1，越大越好。本文通路 A 的 MRR 是 0.908，意味着正确答案平均排在第 1.10 位。
- **Recall@K**：相关答案被召回的比例。

### Q7. 什么是 Pydantic？为什么用 v2？
Pydantic 是 Python 里基于类型注解的数据校验库，把 dict 或 JSON 强制校验为带类型的 Python 对象。v2 用 Rust 重写，校验速度比 v1 快 5~50 倍，且原生支持 OpenAI Function Calling 的 Schema 导出。本文用 Pydantic v2 把大模型返回的 JSON 直接 parse 成 `WeatherIntent` 对象，校验失败立即触发追问，避免错误参数进入下游。

### Q8. 大模型为什么会"幻觉"？
本质是大模型的训练目标是最大化下一个 token 的概率，而不是事实正确性。当训练数据稀疏（如冷门国标条款）或被问到训练截止后的事件时，模型会基于词共现统计"编出"听起来合理的内容。本文识别的 5 类气象幻觉是：引用编造、分级编造、数值漂移、单位混淆、时间窗误判，对应论文 2.1.3 节表 2-2。

### Q9. 沙箱是什么？为什么要受限？
沙箱是把不可信代码隔离在受控环境中执行的机制。本文沙箱要"受限"，是因为大模型生成的代码可能误用 `os.system` 删文件，或调用 `requests` 访问外网，或写出无限循环。本文用四重约束：白名单 builtins 切断危险入口、白名单模块只允许 math/statistics/datetime、墙钟超时 ≤ 5 秒、结构化错误捕获，把风险关进可控盒子。

### Q10. 嵌入向量是什么？1024 维代表什么？
嵌入向量是把文本编码为定长稠密向量的过程，让语义相似的文本在向量空间中距离更近。1024 维表示每段文本用一个 1024 个浮点数构成的向量表示，这是 BAAI/bge-m3 模型的输出维度。维度越高表达能力越强但存储与计算成本越大，1024 是当前中文嵌入模型的主流折中点。

## 二、系统架构与设计选择（"为什么这么做"）

### Q11. 为什么选单 Agent 而不是多 Agent？
气象数据检索分析的工作流相对线性（理解 → 检索 → 计算 → 报告），核心瓶颈不在并行度而在每一步的可信度。多 Agent 会引入额外的协调开销与上下文同步成本，且根据 Q. Wu 等 2023 年 AutoGen 的报告，多 Agent 在垂直业务上的边际收益往往低于单 Agent + 强工具体系。本文 11 个工具 + 受限沙箱已能闭环消解三类问题，引入多 Agent 反而稀释聚焦。如果未来扩展到长时序气候预测等异步任务，再考虑切换。

### Q12. 为什么选 GLM-5.1 而不是 GPT-4o？
两个原因：① 国产化考虑——气象是国家基础信息资源，最终落地要兼顾国产模型；② 成本与可控性——GLM-5.1 通过 SiliconFlow 的 OpenAI 兼容协议调用，每百万 token 成本只有 GPT-4o 的 1/10，且本文核心方法论与具体被测模型解耦，未来切换为 GPT-4o 或本地部署模型不需要修改评测脚本。本文也设了温度 0 以最大化可重复性。

### Q13. 为什么用 LangChain 而不是从头写？
LangChain 0.3 提供的 `create_agent` 与 LangGraph 0.2 的 `InMemorySaver` 已是工业级实现，覆盖了消息历史管理、工具循环编排、流式响应等基础设施。从头写一遍只能在工程上原地踏步，不会带来研究层面的增量。本文聚焦的创新在三件事：双通路 RAG、确定性分级器、受限沙箱，这些都是 LangChain 框架内嵌入的，没有被框架限制。

### Q14. 为什么自己实现沙箱不直接用 Docker？
Docker 启动一个容器需要数秒甚至十几秒，而本文统计任务通常 200ms 内可完成，Docker 的隔离粒度太粗，启动延迟反而是主要瓶颈。本文采用的"白名单 builtins + 白名单模块 + 墙钟超时"的进程内沙箱方案，单次执行 < 50ms，吞吐量与隔离性达到了一个工程上的折中。当然，如果未来要对外开放给非可信用户，会升级到 nsjail / firejail 这类系统级隔离，这一点已在第 6 章未来工作中明确。

### Q15. 为什么是双通路 RAG 而不是单通路？
因为气象问题天然分两类：一类是概念性查询（"梅雨季是什么"），关心相关度排序，向量 + BM25 混合检索就够了；另一类是数值到等级的映射（"35 度算几级高温"），关心精确归属，必须用确定性分级器，不能交给概率模型。强行用单一通路会两头都做不好——纯检索无法保证等级编号唯一对应，纯规则无法覆盖开放式概念查询。两通路在 71 条桥接评测上的对比也证实了这一判断。

### Q16. 三档补全策略的阈值是怎么定的？
三档分别是默认值补全、上下文继承、显式追问，触发顺序是固定的而不是阈值控制的：先尝试默认值（如单地点单时刻查询补全 hours=24h），不行再尝试上下文继承（多轮对话中沿用历史地点），都不行才显式追问用户。这个分层逻辑是基于 35 条意图评测中的失败模式归纳出来的——评测前两轮发现 70% 以上的缺失字段都能用前两档兜底，只有 < 30% 真正需要追问，所以做了这个分层节流。

### Q17. 为什么意图识别要分两阶段？合并成一步不行吗？
合并成一步会让 prompt 同时承担"判断属于哪类意图"和"补全所有参数"两个目标，导致 prompt 过长、失败模式纠缠。两阶段拆开后，第一阶段只用 Pydantic Schema 强制结构化输出，错了立即重试或追问；第二阶段在已知意图类别的前提下针对性补全。35 条评测端到端通过率 91.4% 的结果说明这种解耦的工程效益是显著的。

### Q18. 为什么知识库只有 62 条？太少了吧？
62 条不是知识库的全部容量，而是经过两轮人工核对后保留的高置信度条目。本文的核心立场是"宁缺毋滥"——知识库每多一条错误条目，下游引用真实性就会被污染。论文 5.1 节也披露了一个反直觉发现：知识库从首轮 38 条扩展到 62 条之后，错误率不降反升（首轮 34.2%，二轮新增 57.9%）。这说明知识库扩展必须配合人工核对，规模本身不是目的，可信度才是。

## 三、双通路 RAG 与语义桥接（核心创新点 1 的抓问）

### Q19. `grade_id` 具体长什么样？举个例子
`grade_id` 是论文设计的等级编号硬链接 ID，形如 `heat_level_2`、`fog_level_3`、`rain_level_intense`，在 5 类分级器返回的结构化标签中作为主键。它的作用是把"35°C → 高温二级预警"这一映射通过确定性 ID 锁死，避免大模型在生成报告时把"二级"写成"三级"或编造不存在的等级。本文 71 条桥接评测中 `grade_id` 准确率 100%，就是这一硬链接机制的直接证据。

### Q20. 5 类确定性分级器具体是哪 5 类？
对应气象业务中最常被自然语言混淆的 5 类数值阈值：① 高温分级（GB/T 29457-2012）；② 低温寒潮分级（GB/T 21987-2017）；③ 降水强度分级（GB/T 28592-2012）；④ 雾分级（GB/T 27964-2011）；⑤ 风力等级（GB/T 28591-2012）。每类分级器都是一段几十行的 if-elif 规则，输入数值、输出 `(grade_id, grade_name, citation)` 三元组，无任何概率成分。

### Q21. 通路 A 的混合权重是多少？怎么调的？
向量检索权重 0.6 + BM25 权重 0.4，是在 60 条检索评测集上做了 5 组权重组合（纯向量 1.0、0.7+0.3、0.6+0.4、0.5+0.5、纯 BM25）后选出 Top-1 命中率最高的一组。这个权重对气象领域是经验值，不一定迁移到法律或医疗，但论文中已说明权重在 ChromaDB + rank_bm25 的混合检索类中是可调超参，下游使用者可以按自己的领域重新搜索。

### Q22. 通路 B 桥接前后的对比，桥接前模型到底看到了什么？
桥接前模型只看到孤立的数值或描述，例如"明天最高温 35 度"，它会基于词共现统计编出像"GB/T 20484 §3.0.4 高温二级"这种听起来合理但实际上 GB/T 20484 是寒潮等级标准、不存在该条款的引用。桥接后模型看到的是 `grade_id=heat_level_2` + `grade_name=高温二级预警` + `citation=GB/T 51120-2015` 三段结构化标签，完全消除了引用编造空间。论文 4.1 节有完整的两栏代码对比块。

### Q23. 通路 A Top-1 85.0% 看着也不算高，剩下 15% 怎么办？
剩下 15% 主要是两类失败：① 长尾术语（如"霾"在不同地区的本地称谓）召回偏差；② 多义词（如"暴雨"既指降水强度等级也指预警等级）。补救机制是 ReAct 循环中允许 Agent 在检索结果置信度低于阈值时主动追加 Top-3 检索或转向通路 B 的精确查询，30 条端到端评测中也观察到这种"通路 A 兜底失败时通路 B 接棒"的协同行为。

### Q24. 为什么 71 条桥接评测的 `grade_id` 能做到 100% 准确率？
因为通路 B 是确定性规则，而 71 条评测全部落在 5 类分级器覆盖的数值区间内。这个 100% 不是说通路 B 永远不会错，而是说在评测覆盖的标准国标条款范围内不会错。如果用户问的是 5 类之外的（比如紫外线指数 6 级国标），通路 B 直接返回"无对应分级器"由通路 A 兜底，论文 4.1.3 节明确了这一回退机制。

## 四、代码生成与受限沙箱（核心创新点 2 的抓问）

### Q25. 沙箱超时阈值为什么是 5 秒？
基于 18 条评测集的代码长度与统计任务复杂度估计：本文 6 类统计模式的典型代码不超过 30 行，单次执行通常 < 200ms。5 秒留出 25 倍以上的安全余量，既能容忍偶发的 IO 抖动，又能在大模型不慎生成无限循环时及时熔断。如果未来开放更复杂的统计任务（如十年时序回归），会调到 30 秒并加上 CPU 时间限制。

### Q26. 为什么白名单只允许 math / statistics / datetime？
这三个是统计计算的最小可用集——math 提供基础数学函数、statistics 提供均值方差等统计量、datetime 处理时间窗。numpy / pandas 没加白名单是出于代码注入风险考虑（pandas.read_csv 可读任意文件路径），如果任务真的需要 numpy，未来可以为它单独包一层"只暴露 array 创建与算术运算"的 wrapper。这个白名单是工程权衡，不是技术上限。

### Q27. 88.9% 比 LLM 直算的 66.7% 高 22.2 pp，能再分析一下失败的 11.1% 吗？
18 条中失败的 2 条都集中在"伴随状态维护"任务（例如统计某区间内连续 3 天降水超过 25mm 的次数），这类任务需要在循环过程中维护一个计数器与状态机，大模型生成代码时容易把"连续"误解为"累计"。失败模式分析也写在论文 4.2 节，是后续工作要重点改进的方向之一。

### Q28. 大模型生成的代码安全性怎么保证？
三道防线：① Schema 强制——生成的代码必须导出 `compute(data)` 顶层函数，签名不符直接拒绝执行；② 静态扫描——执行前用 ast 模块解析检查是否有 import 黑名单模块、是否有 eval/exec/__import__ 调用；③ 运行时隔离——白名单 builtins + 墙钟超时。即便上述都被绕过，sandbox 进程本身也是无 root 启动，对外网无访问权限。

### Q29. 代码生成失败了怎么办？
LLM 第一次生成的代码如果语法错或执行抛异常，结构化错误捕获会把异常类型与堆栈片段回填给主智能体，触发一次重试。如果两次都失败，主智能体会降级为"用自然语言告诉用户：本次统计计算暂不可用，请使用 [...] 替代查询路径"，避免给出错误数字。论文 4.2 节有完整的错误恢复状态机描述。

## 五、评测方法论与数据真实性

### Q30. 214 条评测用例是怎么来的？人工写的吗？
是的，全部 214 条都是人工构造，分两批：第一批 130 条由作者基于真实业务场景手写并标注期望输出，第二批 84 条由 3 位非作者的同学从给定知识库中独立挑选生成，避免作者本人盲点。两批用例都遵守"真实数据为底，结构化断言为锚"原则——所有用例基于真实国标与真实 API 返回值，断言只断言结构性证据（如"必须含温度数值"、"必须出现 GB/T 编号"）而不直接断言具体数值。

### Q31. 评测集会不会被大模型预训练过？
风险存在但已被三重缓解：① 评测集 jsonl 文件未公开发布到任何在线平台直到论文答辩通过，预训练污染概率极低；② 评测断言是结构性而非字面，即使模型记住了某条原文也无法直接命中；③ 端到端评测的 30 条用例采用作者本人 2026 年 5 月才确定的查询模板，落在所有公开 LLM 训练截止之后。这一点论文 5.1 节已说明。

### Q32. 91.4%、85.0% 这些数字跑了几次？方差多大？
评测全程温度设为 0 以最大化可重复性。在意图识别评测上同一份评测集独立跑了 3 次，3 次结果分别是 91.4%、91.4%、94.3%，前两次完全一致是因为 GLM-5.1 在温度 0 时对相同 prompt 输出相同结果，第三次的偏差源于 SiliconFlow 后端的非确定性 batching。论文报告的是中位数，并在 5.7 节本章小结明确说明"非零方差源于平台层 batching 不可控"。

### Q33. LLM-as-judge 怎么保证打分公平？
三个工程加固：① 评分 LLM 与被测 LLM 不同源（被测 GLM-5.1，评分用 GPT-4o-mini）避免同源偏好；② 评分 prompt 含完整 rubric 与 4 个 few-shot 评分案例，按事实性、完整性、专业性、流畅性四维独立打分；③ 30 条端到端评测随机抽 6 条由作者人工复核，与 LLM-judge 评分 Spearman 相关 0.83，证明打分一致性可接受。

### Q34. 和风天气与 Open-Meteo 返回值会随时间漂移，评测怎么稳定？
两层稳定性保证：① 模块层评测的断言是结构性证据（"必须含温度数值"），不是具体温度，API 漂移不影响断言通过；② 端到端评测在每次执行前对 API 返回的原始 JSON 做 SHA-256 留档，论文报告的结果都附了对应的 API 留档时间戳（5.1 节表 5-1 的脚注），评审可比对验证。

### Q35. 评测用例数量为什么这么不均匀？意图 35 条、桥接 71 条、代码 18 条？
按"评测对象本身的复杂度与失败模式多样性"分配。桥接评测要覆盖 5 类分级器 × 不同数值边界共 71 个边界点，是天然的多。意图识别 10 类 × 平均 3-4 个变体共 35 条够覆盖。代码评测 6 类统计模式 × 平均 3 条共 18 条，再多就是同一模式的重复。这是论文 5.2-5.6 节按评测对象复杂度做的工程权衡，不是为了凑数。

## 六、评测数据细节抓问

### Q36. 端到端评测中 `decision_support` 类用例从 50% 提升到 100%，原始数字是几条？
`decision_support` 类共 6 条用例（30 条端到端评测中的一类）。`ablated` 档去 RAG 后通过 3 条占 50%，`full` 档启用双通路 RAG 后通过 6 条占 100%。绝对数字不大，但 6/6 vs 3/6 的对比已经能说明 RAG 在决策支持类任务上的关键作用。

### Q37. `full` vs `ablated` 的 13.4 pp 差距统计上显著吗？
30 条用例对应 26 vs 22 通过，做单侧 McNemar 配对检验 p ≈ 0.07，在 α=0.05 水平边缘不显著但 α=0.10 显著。论文 5.7 节诚实地报告了"30 条样本量下统计功效有限"，并把"扩大端到端评测规模到 100 条以上"列入未来工作。

### Q38. 权威标准引用率从 0% 到 26.7%，剩下 73.3% 没引用算失败吗？
不算失败。30 条端到端评测中只有一部分用例（约 8 条）属于"必须引用国标条款才算合格"的强引用类，其他 22 条是"友好对话 + 数据支撑即可"的弱引用类。所以 26.7% 是相对全部 30 条的覆盖率，而 0% 是 ablated 档完全没引用。论文 5.6 节表 5-X 列了引用类型分布。

### Q39. 知识库 24 处问题里 4 处是"业内惯例错标 official"，具体是什么意思？
比如气象业务里"高温红色预警 ≥ 40 度"是中央气象台的业务惯例，但首轮知识库构建时把它标成 GB/T 国标，实际上没有任何国标这么规定。这类问题特别隐蔽——条款编号看起来对、阈值看起来对，但来源被错标为 official 会让下游引用真实性评测失败。这就是知识库扩展过程中"不省略人工核对"这一论断的核心证据。

### Q40. 多地点角色识别准确率 100% 是不是太理想了？
35 条意图评测中只有 8 条是多地点用例（如"明天早八到晚六从武汉到成都的穿衣建议"），8 条全部正确所以是 100%。如果再扩展到三地点接力或更复杂时空交叉，预期准确率会下降。论文 5.2 节也提示"小样本下的 100% 不能外推"，这点会在答辩中坦诚承认。

## 七、学术贡献与创新性辩护（高频锐问）

### Q41. 你和 ChatGPT 直接调气象 API 的本质区别在哪？
本质区别是引入了"确定性桥接层"——通路 B 5 类分级器与受限沙箱。直接调 API 的 ChatGPT 拿到原始数值后，仍然要靠概率模型自己解读"35 度算几级"，引用编造率会很高（论文 ablated 档 0% 引用率就是这种情况）。本文的桥接层把概率推理与确定性归属物理隔离，让大模型只负责自然语言生成，不负责数值阈值判断与条款引用，把可信度从工程层面焊死。

### Q42. 双通路 RAG 是你原创吗？
混合检索（向量 + BM25）不是原创，是 2020 年以来 IR 领域的成熟方案。本文的原创点在于"混合检索 + 确定性分级器"这一组合的双通路结构，以及 `grade_id` 硬链接的设计。把概率检索与规则归属拼接到同一个 RAG 接口下、并通过 71 条桥接评测系统验证两者各自的边界与协同效应，目前公开文献中我没有看到完全相同的工作。这是工程层面的创新，不敢声称是理论突破。

### Q43. 受限沙箱概念早就有了，你的创新点在哪？
沙箱本身确实不是新概念。本文的工程贡献在于把它和大模型代码生成做了端到端集成：① Schema 强约束（必须导出 compute(data) 顶层函数）；② 三层结构化错误反馈机制（失败时把异常类型回填给 LLM 触发重试）；③ 18 条评测系统量化了它相对 LLM 直算的 +22.2 pp 收益。把"沙箱可以这么用"和"沙箱用了之后效果有多大"两件事都做实了。

### Q44. 整篇论文最核心的贡献是哪一项？
是双通路 RAG 中的通路 B——确定性分级器加 `grade_id` 硬链接。这是全文唯一一个把"大模型不可信"问题在工程层面物理消解（而非概率缓解）的设计，对应的 100% `grade_id` 准确率与 100% 引用真实性也是全文最强的量化证据。其他四项贡献更多是工程组合，通路 B 是方法层面的真实增量。

### Q45. 如果只能保留一项，你保留哪一项？
保留通路 B。理由同上——它是方法层面而非工程层面的贡献，且复用门槛最低：任何垂直领域只要有可枚举的分级标准（医疗的检验值分级、金融的风险等级、法律的量刑档），都能复用这套"概率检索 + 确定性归属"的双通路设计。其他四项贡献的复用都需要重新做大量工程适配，通路 B 只需要替换分级规则。

### Q46. 五项贡献中哪一项你觉得最弱？
最弱是第一项——异构 API 统一封装。坦白说这一项更多是工程苦力，技术新意不强，做的就是把和风天气与 Open-Meteo 两类 API 的字段、错误码做统一映射。它的价值在于让后面四项贡献有一个干净的工具调用底座，但单独拿出来看，类似的工作工业界已经做过很多。我在论文里没有过分强调它的创新性。

### Q47. 论文的局限性是什么？
三个局限会在答辩中坦诚承认：① 单 LLM 单数据源——只测了 GLM-5.1 + 和风/Open-Meteo，未做跨模型跨数据源对比；② 评测规模有限——214 条用例覆盖了核心场景但端到端 30 条样本量偏小，统计功效不足；③ 知识库覆盖窄——只覆盖 5 类气象分级标准，未触及大气化学、海洋气象等更细分领域。对应改进方向已在第 6 章未来工作中明确。

## 九、应用价值与未来工作

### Q53. 模块层 → 集成层的衰减效应具体是什么？怎么解释？
模块层评测时各模块独立给定理想输入（意图识别只评意图、检索只评检索），单项指标都很高。集成到端到端时，模块 A 的 92% 输出 × 模块 B 的 90% 输入兼容率 × 模块 C 的 88% 处理率 = 端到端 73% 左右，比任何单模块都低。本文 86.7% 的 full 档通过率已经压过了纯乘性预测，说明 ReAct 循环的失败重试机制吸收了一部分模块间错误。但衰减效应仍然是客观存在的，未来需要显式对话状态跟踪来进一步消解。

### Q54. 显式对话状态跟踪是什么？怎么做？
当前系统的对话状态完全靠 LangGraph `InMemorySaver` 隐式维持，本质是把历史消息原样喂回给 LLM，对长对话会受 context window 限制。显式状态跟踪是用一个独立的 `DialogState` 对象记录"当前任务进度、已确定的参数、待补全的字段、失败的工具调用"等结构化信息，每轮对话只把 `DialogState` 摘要而非原始消息回填给 LLM，能在 50 轮以上的长对话中维持上下文一致性。这是论文 6.2 节的第一项未来工作。

### Q55. 知识库扩展后错误率为什么反而上升？
两个原因：① 选择偏差——首轮 38 条都是最高频最熟悉的标准，作者的核对最仔细；二轮新增 19 条是低频长尾标准，核对时容易疲劳出错。② 标准本身的复杂度——高频标准条款简单清晰，低频标准（如行业规范、地方标准）经常多版本并存且口径不一致。论文 5.1 节给出的"复用同样的标准引用模式并不能保证不出错"这一发现，是对"知识库越大越好"这一直觉的有力反驳。

### Q56. 这个系统能落地到生产环境吗？还差什么？
能落地到内部使用但未到生产级。还差三件事：① 安全沙箱升级为系统级隔离（nsjail/firejail），目前的进程内沙箱不抗对抗攻击；② API 限流与计费追踪，和风天气是商业 API 有调用配额；③ 用户身份与权限管理，当前是单用户原型。这三件事工程量约 1-2 个月，不涉及方法论变更，不在本文研究范围。

### Q57. 谁会用这个系统？商业化可能性？
潜在用户两类：① 县级气象局或基层应急部门，需要快速把气象数据转化为决策语言，但缺乏专业气象人员；② 户外作业行业（建筑、农业、物流）的运营部门，需要按业务场景查询气象指标。商业化路径不是直接卖系统，而是把核心方法论（双通路 RAG + 确定性桥接）做成一个垂直领域可信 LLM 框架，每个新领域复用 80% + 定制 20%。

### Q58. 这个系统比直接打 12121 天气电话好在哪？
12121 是单向广播，只能听到城市级别的标准化天气预报。本文系统支持自然语言交互（"明天我从武汉骑行到红安，要带雨衣吗"），能针对用户具体场景做小时级精度的多地点查询，并自动引用国标条款解释为什么建议带雨衣。这种交互式 + 可解释的能力是 12121 不具备的，但代价是计算成本与延迟。

### Q59. 未来如果 GLM 升级到 GLM-6 或 GLM-7，你的工作会过时吗？
不会，反而会受益。本文的方法论核心是"确定性桥接 + 受限沙箱"，与具体被测模型解耦。如果 GLM 升级让自由发挥的基线从 12% 引用真实性涨到 50%，本文方案的 100% 引用真实性优势会缩小，但绝对值仍然更高。同时方法论的可复现性、可审计性是任何概率模型都无法替代的——这些价值随模型升级反而更突出。

### Q60. 这个工作和气象局现在用的预报系统有什么关系？
互补关系，不是替代。气象局现有系统（如数值预报模式、雷达拼图、卫星反演）解决的是"数据从哪来"，本文系统解决的是"数据到决策语言之间的最后一公里"。气象局 90% 的精力在前者，但用户感知到的痛点 90% 在后者。如果未来能和气象局的内部系统对接，本文系统可以作为一个轻量级的对外咨询接口，把专业数据翻译成普通用户能理解的决策语言。

## 十、论文写作与形式问题（小概率但要会答）

### Q61. 摘要为什么分 3 段？
按学位论文规范要求：第一段背景与问题、第二段主要研究工作、第三段主要结果与结论，方便评审快速把握论文结构。这一格式也是按照导师在评审意见中的明确要求修改的。

### Q62. 关键词为什么是"大语言模型"和"智能体"分开两个？
这两者是当前学界与工业界都广泛承认的两个独立技术领域：大语言模型关注模型本身的训练与能力，智能体关注模型对外的工具调用与任务执行。把它们分开作为关键词，对论文的检索性更友好——感兴趣 Agent 但不关心 LLM 的研究者，或者反之，都能各自命中。

### Q63. 为什么有附录 A？
附录 A 列出 GitHub 仓库地址 + 简要说明，目的是让评审能在课后访问完整源代码、知识库、评测集与评测结果原始 JSON，验证论文报告数据的可重现性。这是答辩规范中"研究可复现性"原则的工程承载。

### Q64. 论文里的"三类技术问题"和"五项创新贡献"是什么对应关系？
- 指令解析问题 ↔ 贡献 1（API 统一封装）+ 贡献 2（双阶段 NLU）
- 异构数据问题 ↔ 贡献 1（API 统一封装）+ 贡献 3（双通路 RAG）
- 数值与逻辑幻觉问题 ↔ 贡献 3（双通路 RAG）+ 贡献 4（受限沙箱）
- 跨越所有三类问题 ↔ 贡献 5（多层评测体系）

不是 1-1 映射，因为每一类问题的解决都涉及多个工程环节，每个工程环节也在解决多类问题。论文 1.3 节给出了完整的对应表。
