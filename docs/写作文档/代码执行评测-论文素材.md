# 代码生成 + 沙箱执行 vs LLM 自由直算：消融对照实验

> **用途**：本文档作为毕业论文素材，记录在 `data/test_cases/code_exec_bench.jsonl`
> （**18 条**统计分析任务，覆盖平均/极值/求和/差值/计数/排序六类）上对比
> 两种范式——「LLM 自由发挥直算」与「LLM 生成代码 + 受限沙箱执行」的
> 数值准确率，作为论文 Q3 章节"为什么必须做代码执行"的核心实证。
>
> **评测时间**：2026-05-04

> - `src/analysis/code_generator.py`（LLM 代码生成）
> - `experiments/eval/code_baseline.py::run_llm_direct`（LLM 直算 baseline）
>
> **评测脚本**：`experiments/eval/run_code_eval.py`
> **指标定义**：`experiments/eval/code_metrics.py`
> **结果文件**：`experiments/results/code_eval_latest.md`

## 一、评测集设计：18 条任务覆盖 6 类统计模式

每条用例形如：

```json
{
  "id": "avg_001_max_temp_week",
  "category": "average",
  "query": "过去一周武汉每天最高温的平均值是多少摄氏度？保留 1 位小数。",
  "data": {"city": "武汉", "daily": [{"date": "...", "tempMax": 18.5, "tempMin": 8.2}, ...]},
  "expected": {
    "value": 20.4,
    "tolerance": 0.05,
    "type": "scalar",
    "ground_truth_explanation": "(18.5+20.3+22.7+19.0+16.5+21.4+24.1)/7=142.5/7=20.357..."
  }
}
```

### 1.1 任务分布

| 类别 | 用例数 | 任务设计要点 |
|---|---:|---|
| `average` | 5 | 含整除（12.5）、近似（69.83）、保留 2 位（4.04）、银行家舍入边界（24.95） |
| `extreme` | 3 | 找最高温/最大降水/最低温对应的日期或时刻 + 数值 |
| `sum` | 2 | 7 天累计降水（327.4） + 条件求和（仅高温日的累计降水） |
| `diff` | 4 | 日较差最大、温度极差（max-min 跨日）、同比降水差、平均日较差 |
| `count` | 2 | 下雨天数（precip>0）、高温阈值天数（含 `35.0` 边界） |
| `sort` | 2 | 降水前 3 名日期、第二高温日期 |
| **合计** | **18** | 涵盖统计学常见模式 + 边界情形（舍入、阈值平等、跨年比较） |

### 1.2 期望类型分布

| `expected.type` | 用例数 | 说明 |
|---|---:|---|
| `scalar` | 12 | 单一数值，含 tolerance |
| `date_with_value` | 3 | 字典 `{date, metric}`，要求两个字段都对 |
| `time_with_value` | 1 | 字典 `{time, metric}` |
| `ordered_list` | 1 | 顺序敏感的字符串列表 |
| `date` | 1 | 单一日期字符串 |

`*_with_value` 是评测的关键设计——既要 LLM 答出"哪一天"，又要给出对应的数值。
这种"复合答案"是 LLM 直算的典型痛点（详见第 3 节）。

## 二、实验三档与核心数据

### 2.1 三档消融架构

| 档位 | 处理流程 | 角色 |
|---|---|---|
| `oracle` | 直接读 `expected.value` | 评测器自校验天花板 |
| `llm_direct` | LLM 看 `query + data`，**禁止生成代码**，直接给 `value` | LLM 自由发挥的对照 |
| `llm_with_code` | LLM 生成 `compute(data)` 代码 → 受限沙箱执行 → 取返回值 | 工具学习 + 代码执行的核心方案 |

`llm_with_code` 的代码执行环境（`src/tools/code_executor.py`）：

- **白名单 builtins**：仅 `abs/sum/max/min/round/sorted/zip/iter/next/len/...`
  + 显式黑名单 `open/eval/exec/__import__/input/breakpoint`
- **白名单模块**：仅 `math`、`statistics`（无 `os/sys/subprocess` 等任何 I/O）
- **墙钟超时**：默认 5 秒（用 `threading.Thread(daemon=True) + join(timeout)`，
  Windows 兼容；超时后线程作为 daemon 后台残留，不阻塞主流程）
- **结构化错误**：所有失败模式（语法/缺函数/超时/运行时异常）统一通过
  `ExecutionResult` 返回，不抛异常污染上游

### 2.2 核心结果（18 条 / 3 档）

| 指标 | oracle | llm_direct | llm_with_code |
|---|:---:|:---:|:---:|
| **数值准确率（核心）** | 100.0% | **66.7%** | **88.9%** |
| 代码生成率 | — | — | 94.4% |
| 代码可执行率 | — | — | 94.4% |

**核心差距：22.2 pp**（66.7% → 88.9%），代码执行档明显优于 LLM 自由直算。

### 2.3 按类别拆分（仅看数值准确率）

| 类别 | 用例数 | llm_direct | llm_with_code | 差距 |
|---|---:|:---:|:---:|:---:|
| `extreme` | 3 | **0.0%** | 66.7% | **+66.7 pp** |
| `count` | 2 | **50.0%** | 100.0% | **+50.0 pp** |
| `average` | 5 | 80.0% | 100.0% | +20.0 pp |
| `sum` | 2 | 100.0% | 100.0% | 持平 |
| `sort` | 2 | 100.0% | 100.0% | 持平 |
| `diff` | 4 | 75.0% | 75.0% | 持平（含命名约定问题） |

**关键观察**：

1. **极值任务差距最大（+66.7 pp）**：LLM 直算在 3 条 `extreme` 用例上**全军覆没**——
   不是因为它不知道答案（reasoning 字段里都明确说了"03:00 最低 -19.3°C"），而是因为
   **结构化输出 schema 不稳定**——它只给了日期 / 时刻字符串，没把数值放进 `numeric_extra`。
2. **条件计数差距 +50 pp**：LLM 直算把"7 天"数成"6 天"（reasoning 列出 7 个日期却写"6 天"）。
3. **简单求和与排序持平**（100% 都对）：在不需要复杂状态维护的任务上，LLM 凭语料能力可以做对。
4. **差值类持平在 75%**：代码档的失败是字段命名漂移（`range` vs `tempDiff`），算法逻辑正确。

## 三、典型失败模式归类（论文论点核心）

下面四类是 LLM 直算的典型幻觉模式，每类都有真实案例支撑。

### 3.1 数数错误：reasoning 自相矛盾

**用例 `count_001_rainy_days`**：14 天里有几天下雨（precip > 0）？

**正确答案**：7 天（04-02, 04-03, 04-05, 04-08, 04-09, 04-12, 04-14）

**LLM 直算输出**：
- `value`: 6
- `reasoning`: "降水量>0的天数为 **6 天**：4月2日(2.3)、3日(0.5)、5日(15.8)、
  **8日(4.7)、9日(12.4)**、12日(1.8)、14日(3.2)"

**幻觉特征**：reasoning 中**列出了正确的 7 个日期**，但断言句里写"6 天"。
这是最危险的幻觉模式——表面看起来 LLM 在认真"列举推理"，实际计数与列表不一致。
用户读 reasoning 大概率被说服。

> **代码档对照**：`compute(data)` 用一行 `sum(1 for d in daily if d["precip"] > 0)`
> 直接得到 7，**绝不会犯计数错误**。

### 3.2 舍入不一致：教科书 vs 银行家舍入

**用例 `avg_005_feels_like`**：8 小时体感温度均值，保留 1 位小数。

**正确答案**：24.9（`round(24.95, 1)` 用 IEEE 754 银行家舍入向偶数舍入 → 24.9）

**LLM 直算输出**：
- `value`: 25.0
- `reasoning`: "199.6/8=24.95，保留1位小数为 **25.0**"

**幻觉特征**：LLM 用的是中学教科书"四舍五入"（24.95 → 25.0），而 Python `round` 用
银行家舍入（24.95 → 24.9）。这是一个**语境敏感的精度幻觉**：在工程数据处理中
默认就该按 Python 标准舍入，但 LLM 凭语料习惯按"日常四舍五入"作答。

> **代码档对照**：`statistics.mean(...)` + `round(value, 1)` → 自动用 Python 标准舍入，
> 与下游所有数值处理保持一致。

### 3.3 Schema 不稳定：复合答案被压缩成单字段

**用例 `extreme_001_hottest_day` / `extreme_002_max_precip_day` /
`extreme_003_coldest_hour` / `diff_001_max_diurnal`**（4 条）：要求同时给出
"哪一天/时刻"和"对应数值"。

**期望格式**：`{"date": "2025-07-03", "tempMax": 36.8}`

**Prompt 已显式声明**：
> 当用户问的是"哪一天"或"哪个城市"时，``value`` 应是日期串或城市名（字符串），
> 同时把对应数值放在 ``numeric_extra`` 字段

**LLM 直算实际输出**（4 条全部）：
- `value`: `"2025-07-03"`（仅字符串）
- `numeric_extra`: `null`（未填）
- `reasoning`: "7天中2025-07-03的最高温36.8°C为最大值"（reasoning 中给出了数值，但没结构化）

**幻觉特征**：即使 prompt 明确给出双字段输出指引，LLM 在 `function_calling` 模式下
仍**不稳定遵循 schema**——它知道答案，但只会把"主答案"塞进 `value`，把"辅助
数值"留作自由文本。这是 LLM 应用工程中的经典痛点：**结构化输出的可靠性
随 schema 复杂度上升而急剧下降**。

> **代码档对照**：`compute(data)` 直接 `return {"date": ..., "tempMax": ...}`，
> 字典字段确定性返回，不存在结构不全的可能。

### 3.4 字段命名漂移（代码档失败模式）

**用例 `diff_001_max_diurnal`**：找出日较差最大的一天 + 温差值。

**期望**：`{"date": "2025-09-18", "tempDiff": 22.7}`

**代码档实际**：`{"date": "2025-09-18", "range": 22.7}`

**LLM 生成的 code**：

```python
def compute(data):
    daily = data["daily"]
    max_range = -1
    max_date = None
    for day in daily:
        diff = day["tempMax"] - day["tempMin"]
        if diff > max_range:
            max_range = diff
            max_date = day["date"]
    return {"date": max_date, "range": round(max_range, 1)}
```

**幻觉特征**：算法**完全正确**，但 LLM 把字段命名为 `range`（语义合理），
而评测期望是 `tempDiff`。这反映了**LLM 在数据建模时的命名约定不严格**——
即使 prompt 提供了相同变量在 query 中的描述（"日较差"），生成代码时仍可能
选择不同的命名方案。

> **工程含义**：这一类失败在生产环境可以通过两种方式规避：
> 1. **更严格的 schema 约束**：在 prompt 中显式声明返回字典的精确字段名
> 2. **结果适配层**：在 `execute_code` 后增加 schema validator，对 dict 字段做模糊匹配
> 论文中可作为"未来工作"展开。

## 四、论文写作可引用要点

### 4.1 论证 Q3 章节"为什么必须做代码执行"

```
LLM 直算   数值准确率 = 66.7%
代码执行   数值准确率 = 88.9%
差距 = 22.2 pp
```

这是与"双通路 RAG（A+B）+ LLM hallucination"完全**正交**的论证维度——
前者证明 LLM 在**知识引用**上不可信，本节证明 LLM 在**数值计算**上同样不可信。
两条独立证据共同支撑论文的总论点：**LLM 必须配合工具学习与代码执行才能产生
工程可用的输出**。

### 4.2 Q3 升级版"双指标对比"

把现有 LLM hallucination 的双指标论证扩展为「三维 LLM 不可信谱系」：

| 维度 | 评测对象 | LLM 自由发挥准确率 | 工具/规则/代码兜底准确率 |
|---|---|---:|---:|
| **结构化分级 ID** | 通路 B 67 条 | 0.0% | 100% |
| **权威标准引用** | 通路 B 71 条 | 25.4%（must_cite） | 100% |
| **数值统计计算**（本节） | 18 条 | **66.7%** | **88.9%** |

三个维度各有失败模式，**无一例外都需要外部工具**：
- 引用错误：通路 A（混合检索）召回 + KB 硬链接
- 分级编造：通路 B（确定性 if-else 分类器）
- 数值幻觉：代码生成 + 受限沙箱

这构成了论文方法论的**完整三角架构**。

### 4.3 LLM 在「自由文本」与「结构化输出」之间的认知鸿沟

按类别拆分的差距分布揭示了一个细节：

```
极值任务 +66.7 pp（LLM 直算 0% → 代码 67%）
计数任务 +50.0 pp（LLM 直算 50% → 代码 100%）
平均值 +20.0 pp
求和 / 排序 持平 100%
```

**规律**：LLM 在简单累加（sum）与天然排序（sort）上能力接近代码；但只要任务
需要「**伴随状态维护**」（每次更新最大值时还要记录对应日期）或「**离散计数**」
（条件累加器），LLM 就会犯错。

这与认知科学中"工作记忆容量限制"的发现一致——LLM 的"心算"近似人类心算，
能做无状态的简单计算，但维护中间状态时容易出错。**代码执行就是给 LLM
配一支笔与一张草稿纸**，把"心算"换成"笔算"。

### 4.4 受限沙箱的设计取舍

`code_executor.py` 是一个**轻量原型沙箱**，主动放弃了完整的安全隔离：

- ✅ 屏蔽 `open` / `eval` / `exec` / `__import__` 等高危内置
- ✅ 限制可见模块到 `math` / `statistics` 只读数学库
- ✅ 墙钟超时 5 秒防止意外死循环
- ✅ 异常结构化捕获，不污染主流程
- ❌ 不抵御主动恶意（如 CPU 攻击、内存炸弹、利用 `__class__` 链逃逸）
- ❌ 死循环线程作为 daemon 后台残留，无法真正杀死

设计取舍：**毕设原型的目标不是造一个生产级安全沙箱，而是为「LLM 代码生成
的可靠性」提供可重复测量通道**。完整的安全沙箱（RestrictedPython / Pyodide /
Docker 隔离）属于"未来工作"。

### 4.5 与「知识库标准核对表」的呼应（升级三角闭环）

到目前为止，论文实证体系已经形成四个证据支柱的闭环：

| 实证 | 评测对象 | 关键数据 |
|---|---|---|
| 数据真实性 | KB 12 项标准人工核对 | 7 处错误已修正（`知识库标准核对表-论文素材.md`） |
| 通路 A（检索） | RAG 60 条 / 8 类查询 | top-1 85% / Recall@5 97.7%（`通路A检索评测-论文素材.md`） |
| 通路 B（桥接） | 71 条 / 9 类要素 | grade_id 100% / citation 100%（`LLM幻觉对照实验-论文素材.md`） |
| 意图理解 | 35 条 / 10 类场景 | 端到端 91.4% / 角色 100%（`意图识别评测-论文素材.md`） |
| **代码执行**（本节） | **18 条 / 6 类任务** | **数值准确率 +22.2 pp**（`代码执行评测-论文素材.md`） |

五个评测在数据规模（35 / 60 / 71 / 12 / 18）、研究问题（Q1 / Q2 / Q3）和实证
角度（recognizer 输出 / RAG 召回 / LLM 幻觉 / 标准引用 / 数值计算）上互不重叠，
**形成完整的端到端论证闭环**。

## 五、运行可重现性

```bash
# 单元自检：受限沙箱（6 类边界条件）
python -m src.tools.code_executor

# 单元自检：代码生成 + 执行端到端（3 条样例，约 30 秒）
python -m src.analysis.code_generator

# 完整 3 档消融评测（首次约 4 分钟，缓存后约 5 秒）
python -m experiments.eval.run_code_eval

# 强制重跑（不读两层缓存）
python -m experiments.eval.run_code_eval --force-llm
```

实验结果以 `(timestamp).json` + `.md` 双格式落盘到 `experiments/results/`，
LLM 直算与代码生成的输出分别缓存到独立文件：

- `experiments/results/code_baseline_cache.json`：LLM 直算结果
- `experiments/results/code_gen_cache.json`：LLM 代码生成结果

修改 prompt 字面值会通过 `BASELINE_PROMPT_VERSION` / `CODE_GEN_PROMPT_VERSION`
版本号让缓存自动失效。

### 5.1 评测过程稳定性

参考 `LLM幻觉对照实验-论文素材.md` 中的 SiliconFlow socket idle hang 教训，
本评测脚本同样做了多层加固：

- `code_generator.py` 与 `code_baseline.py` 的 `ChatOpenAI` 实例均带
  `timeout=60` + `max_retries=2`，单次请求最多 ~3 分钟必定返回。
- 每条用例后**增量落盘**两层缓存，主循环包在 `try/finally` 中，保证
  `KeyboardInterrupt` 也能保留已完成进度。
- `code_executor.execute_code` 用 `daemon=True` 线程实现墙钟超时，
  不会因 LLM 生成的死循环代码而阻塞评测。
