# 答辩速查卡：三类研究问题的典型例子

> 答辩时如评委追问"具体是什么样的例子?"或者"为什么说大语言模型有幻觉?",可直接从这份速查卡里挑 1~2 条复述。所有例子均来自论文 2.1 节正文,数据可追溯到 5.4、5.5 节实证。

---

## 一、气象任务指令解析问题

> 核心矛盾:用户用自由口语,API 要严格结构化参数。

### 例 1：相对地点 + 模糊时间 → 严格枚举

- **用户输入**："武汉这周天气如何"
- **目标参数**：和风天气 `get_forcast_weather(LocationID=101200101, hours=168h)`
- **痛点**：`hours` 是枚举值,只允许取 `24h / 72h / 168h` 三选一;"这周"必须先抽象为 168 小时,再映射到合法枚举。

### 例 2：相对历史时间 → ISO 8601 区间

- **用户输入**："去年这个月每小时降水多少"
- **目标参数**：Open-Meteo `[2024-04-01, 2024-04-30]` ISO 8601 字符串
- **痛点**：需同时完成"相对时间消歧 + 字符串格式化",两步任意一步出错都会导致取数失败。

### 例 3：默认值隐含 —— 隐式地点 / 时间补全

- **用户输入 A**："明天天气怎么样" —— 默认查询**所在地**(地点缺省)
- **用户输入 B**："北京天气怎么样" —— 默认查询**当天**(时间缺省)
- **痛点**：缺省字段如果不在前置 NLU 阶段显式补全,ReAct 循环会陷入"猜参数"的低效尝试。

### 例 4：多角色 + 时间段对齐(参数补全最复杂的场景)

- **用户输入**："明天早八到晚六从武汉到成都有什么穿衣建议"
- **隐含结构**：
  - **起点角色**:武汉(出发地)
  - **终点角色**:成都(到达地)
  - **时间段**:08:00–18:00,需对齐到两个城市
- **痛点**:多地点角色识别一旦混淆,会把出发地天气当成到达地天气。本文意图评测中,这一场景 35 条评测的多地点角色识别准确率达到 100%,无一例混淆。

### 例 5：对抗鲁棒性 —— 与气象无关的输入

- **用户输入**："推荐部好看的电影"
- **痛点**：Agent 必须能识别为非气象意图并友好引导,而不是强行解析为某个气象意图、调用错误的工具。

## 二、气象数据异构特征问题

> 核心矛盾:多源、多粒度、多要素,直接拼数据会引发口径混乱。

### 例 1：数据源异构 —— 两个 API 的能力错位


| 维度    | 和风天气             | Open-Meteo         |
| ----- | ---------------- | ------------------ |
| 时间窗口  | 近 30 天 + 未来 30 天 | 历史可追溯到 **1940 年代** |
| 增值能力  | 实时观测、预警、生活指数     | **无预警、无生活指数**      |
| 数据风格  | 商业化、字段中文描述       | 学术化、字段英文缩写         |
| 错误码体系 | 自定义 `code` 字段    | HTTP 状态码           |


**痛点**：地理标识、参数命名、字段命名、错误码体系**完全不一致**,必须在工具层做统一封装,否则上层 Agent 会被多套返回格式淹没。

### 例 2：粒度异构 —— 同名字段在不同接口下含义完全不同

- **逐小时预报** `precip` —— 单位 mm/h(小时累积)
- **逐日预报** `precip` —— 单位 mm/day(日累积)
- **历史归档** `precipitation_sum` —— 日累积量6 
- **典型错误**：把日累积 50 mm 误读为小时累积 50 mm,会把"中雨级别的整日降水"错判为"暴雨级别的单小时强降水",最终决策全错。

### 例 3：要素异构 —— 三种数据形态混在同一会话

- **连续型**:温度、湿度、降水量、风速 —— 浮点数值
- **离散型**:风力等级、能见度等级、生活指数等级 —— 1~12 等阶梯整数
- **事件型**:预警信号(蓝/黄/橙/红)、灾害等级 —— 类别标签
- **痛点**：要直接拼到一段自然语言报告里,必须先把它们对齐到统一的"原始值 → 分级名 → 影响描述 → 标准引用"四元组,否则模型会按最熟悉的"连续数值"模板套到所有要素上,出现"今天风力 7.5 等级"这种错乱描述。

## 三、大语言模型数值与逻辑幻觉问题

> 核心矛盾:LLM 的训练目标是预测下一个 token,在数值精度与权威引用上有内在边界。论文归纳为 5 类典型幻觉。

### 幻觉 1：引用编造(最危险)

- **典型现象**：模型自信地给出 "32 ℃ 已达到高温二级预警,依据 GB/T 20484 §3.0.4 ……"
- **真实情况**：**GB/T 20484 是寒潮等级标准**,根本不存在该条款,被无中生有地挂到了高温场景上。
- **量化**：71 条桥接评测中,LLM 自由发挥档 `grade_id` 完全正确率仅 5.6%,关键引用关键词严格命中率仅 25.4%。
- **致命点**：这种"真实标准号 + 错误场景"的混搭,比纯捏造更难被用户识别,**专家用户也未必能一眼看出**。

### 幻觉 2：分级编造

- **典型现象**：被问"35 mm 降水属于什么级别"时,模型自创 `grading_precip_24h_strong` 这种 `grade_id`。
- **痛点**：自创编号在命名规则上完全合规,**足以骗过基于字符串匹配的下游引用检查**。本文用 `grade_id` 硬链接 + 知识库白名单校验才彻底拦截这类编造。

### 幻觉 3：数值漂移(代码沙箱要解决的核心问题)

- **典型现象**：让模型直接做心算或自由生成统计结果,经常数错、舍入不一致、字段命名漂移。
- **量化**(18 条 6 类统计评测,LLM 自由直算):
  - 整体数值准确率 **66.7%**
  - **极值类任务准确率 0%** —— 模型几乎无法可靠地找出最大最小值
  - **计数类任务准确率约 50%** —— 模型在需要维护伴随状态的离散计数上失败率最高
- **本文方案**：把统计任务从模型内部转移到代码沙箱,准确率提升到 88.9%。

### 幻觉 4：范围错位

- **典型现象**：把日累积 50 mm 当成小时累积 50 mm 来判定降水强度。
- **根因**：模型缺乏稳定的单位与时间粒度记忆,**在不同上下文中对相同数值的解读会发生切换**。
- **后果**：会把同一份数据从"中雨"误判为"暴雨",或反之,**等级跨越多档**。

### 幻觉 5：场景误判

- **典型现象**：在户外高空作业的安全咨询场景下,模型仍输出"今天适合洗车"这种生活提示。
- **根因**：模型默认倾向于在结构化输出场景下也"主动给建议",违反场景过滤约束。
- **后果**：在严肃业务场景中输出消费级建议,严重影响系统专业性。
